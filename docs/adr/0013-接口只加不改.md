# 0013 前台接口只加不改；最低前端版本用 426 引导刷新

- 状态：待定（要点已贴 #63，等所有者无异议后改为「已接受」）
- 日期：2026-11-13　· 拍板：所有者 SMG562
- 相关：Issue #63（第 1 件）· #51（L11 最低系统版本）· `tests/spec/api_spec.md` · `sw.js`

## 背景
上线后会有真用户用着旧版前台：手机 PWA 有 Service Worker 缓存，标签页可能几天不关；我们天天发新版。新旧前台和新接口必须能共存，否则每次发版都会让一部分人出错或白屏。现在没有版本号路径、也没有前台版本标识，接口兼容全靠自觉。

## 决定
**范围**：前台接口 `/api/*`、推送 payload（`sw.js` 读的字段）、通知 / 分享链接格式。后台 `/admin/api/*` 页面与接口同次部署，不受此约束；但开着的旧后台页遇到不认识的错误要提示刷新、不白屏。

**规则**
1. 已发布的字段、错误码、HTTP 状态：不改名、不改含义、不删。
2. 新增请求字段一律可选，不带 = 旧行为；新增返回字段旧前台忽略即可。
3. 枚举 / 错误码可以加新值；前台对不认识的值必须有兜底（通用文案，不报错、不白屏）。
4. 删除走三步：先停用（服务端不再依赖，返回里照留）→ 至少观察一个发布，且「最低前端版本」已越过 → 再删。
5. 破坏性改动必须走新路径（如 `/api/games/create2`），旧路径保留到第 4 条可删时。

**最低前端版本**（与 L11 / #51 分开：L11 管「浏览器跑不动新语法」，这里管「前台代码太旧、接口已不兼容」）
- 前台每个 `/api/` 请求带 `X-NBQ-Build: <构建号>`；服务端有一个「最低构建号」设置，默认不启用。
- 启用后，低于它（或没带这个头）→ 426 `client_outdated`；前台收到后显示「有新版本，点一下刷新」（与 #63 第 3 件 Service Worker 更新提示共用同一条提示），不白屏、不丢登录。
- 只在走了第 5 条破坏性改动、旧路径要下线时才抬最低版本；平时不用。
- 实现（请求头 + 426 + 前台提示）放在 #63 第 3 件的 PR 里；本 ADR 只定做法。

**守卫**：不加新脚本（ADR 0012：脚本数只降不升）；靠 PR 自检「改了 `api_spec.md` 已有字段吗」+ 现有接口测试里的字段断言。

## 否决的方案
- 版本号路径（`/v2/`）/ OpenAPI：2–3 人、一个前台，维护两套路径和描述文件的成本大于收益（#63「不做」）。
- 强制每次发版都抬最低版本：会让开着的页面频繁被要求刷新，打断正在填的表单。
- 什么都不做、靠 Service Worker 自动更新：标签页不刷新就一直是旧代码，SW 管不到正在运行的页面。

## 后果
- 好处：发版不必顾虑旧前台；出现必须破坏的改动时，有一条可控的下线路径（新路径 + 抬最低版本）。
- 代价：字段只增不减，接口会慢慢积累旧字段；删除要多等一个发布。
- 以后变容易：Service Worker 更新提示、426 兜底共用一条提示；变困难：改名 / 改含义要走新路径。

## 什么情况下回头重看
- 出现第二个独立前台（如原生 App），或需要同时支持三个以上前台版本。
- 旧字段积累到影响接口可读性（某个接口一半以上字段已停用）。
- 一个月内因「接口不兼容」导致的线上报错 ≥ 2 次：说明规则没守住，考虑加机器检查。
