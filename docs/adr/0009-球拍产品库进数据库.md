# 0009 球拍产品库放进数据库，前台从接口读；后台管理用两个新权限

- 状态：已接受
- 日期：2026-11-07　· 拍板：所有者 SMG562
- 相关：Issue #60（方案 11-07 03:31，批准 11-07 07:18）· PR #88（A4 产品库）· #89（A5 每晚统计）· #71 · #72

## 背景
「我的球拍」（#60）每人最多 3 把，记品牌 + 系列，球员卡上别人可见。11-06 定的做法是：预设品牌 / 系列放在前台常量里，服务器只校验长度和字符，不管是不是预设里的。

后来要在后台管理产品库（新增、改名、隐藏、合并）、看哪些拍子流行和上升最快，还要把用户自由输入的拍子归进产品库。只放在前台常量里做不到：后台改了要重新发版，服务器也不知道每把拍子对应哪一款，没法统计。

## 决定
1. **产品库进数据库**：新表 `racket_catalog`（品牌、系列、别名、状态 `active` / `hidden` / `merged`、排序）。`user_rackets` 加 `catalog_id`（可以为空）。
2. **前台从接口读选择列表**：`GET /api/rackets/catalog`（不用登录，只返回 `active` 的，缓存 1 小时）。前台保留一份内置常量，**只在接口读不到时兜底**，以数据库为准。
3. **保留「其他」自由输入**：服务器按「去首尾空白、不分大小写、品牌 + 系列或别名」自动归到产品库，归不上的 `catalog_id` 为空，进后台「待归类」。原有校验不变（30 字、拒绝链接 / `@` / 连续 6 位以上数字、不重复）。
4. **统计以数据库为准**：每晚汇总进 `racket_daily`（每天每款的持有人数、主力人数，不含用户）。「上升最快」= 近 7 天持有人数增量，基数不到 5 的不进榜。埋点只用来看流程（打开 → 选品牌 → 保存），不记自由输入的文字。
5. **后台两个新权限**：
   - `racket.catalog`（owner、operator）：管产品库、处理待归类；
   - `racket.moderate`（owner、operator）：清除某个用户的违规球拍文字，要写理由。
   - 两种操作都记进 `admin_audit_log`；viewer 只能看概览。

## 否决的方案
- **继续只放前台常量**：后台没法管理，也没法按款统计；改一次列表就要发一次版。
- **只允许从产品库里选，不留自由输入**：新款、冷门款选不到，用户只能放弃；产品库要靠运营先补全才能用。
- **业务数字靠埋点统计**：关了「使用数据」的用户不会被统计，口径不稳定；数据库里本来就有准确的持有关系。
- **不加新权限，沿用现有后台权限**：清除用户文字会改别人公开显示的内容，和管产品库是两类风险，要分开授权、分开留痕。

## 后果
- 好处：后台可以随时维护产品库，不用发版；用户写得多的自由输入能一键收进产品库，产品库会越用越全；趋势数据只存计数，不涉及个人。
- 代价：多了 3 张表 / 列、一个公开接口、一个每晚任务、两个权限，要测试和迁移；前台多了一次读取和兜底逻辑。
- 隐私：「下载我的数据」导出球拍时同时给出用户写的文字和产品库里的名称（#71）；隐私清单补上统计和待归类两行（#72）。

## 什么情况下回头重看
- 产品库超过约 500 条，或者 1 小时缓存导致用户看不到新加的款式；
- 自由输入占比长期高于 30%（说明自动归类或产品库没起作用）；
- 以后要加球鞋、线等其他装备时：另建表，不在 `racket_catalog` 上泛化。
