# 架构决策记录（ADR）

**为什么有这个目录**：重大的技术 / 产品架构决定，原来散在 `进度记录_历史.md` 里，新人（和 AI 助手）找不到「为什么这么做」，就会重复讨论、甚至悄悄推翻。ADR 把每个决定固定成一页：背景、决定、否决了什么、什么情况下回头重看。

## 什么时候要写
- 改公共接口、数据库结构的原则、目录结构、登录 / 数据 / 隐私的做法、选用或替换某个服务 / 框架
- 一个决定会让后来的人问「为什么不是 X」
- 不要写：普通功能、小修、纯视觉调整（那些在 Issue / PR 里）

## 怎么写
1. 复制 `0000-模板.md`，编号取下一个，文件名 `NNNN-短标题.md`
2. 在 Issue 里讨论并由所有者拍板后，把结论写成 ADR，**和实现放在同一个 PR 或先于它合并**
3. 状态只有四种：`待定`（草案，未拍板，不要按它开工）· `已接受` · `已取代（被 NNNN）` · `已废弃`
4. 已接受的 ADR **不改结论**；想推翻就写新的 ADR 并把旧的标为「已取代」
5. 只写有依据的事实：每条 ADR 末尾写「来源」（Issue / 进度记录 / 提交）。**口头说过但没记录的，先让所有者确认再写**。

## AI 助手
开工前如果任务碰到某个决定的范围，先读对应 ADR；与 ADR 冲突时**停下来问**，不要自己绕开。
