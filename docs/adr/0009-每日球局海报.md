# 0009 每日球局海报：9:00 冻结快照，CI 出图，私有存放，后台下载 + 邮件

- 状态：**待定**（草案，等所有者拍板 §8 的 D1–D9；**未拍板前不开工**）
- 日期：2026-11-08　· 拍板：（所有者）
- 相关：新需求「每天 9 点汇总墨尔本第二天还缺人的球局 → 生成小红书配图 → 后台可下载 / 发邮件」

## 背景
早期每天在小红书发帖推广。需要每天 9:00（墨尔本时间）自动汇总**明天**还在找人的公开球局：≤10 局出「时刻表」海报，>10 局出「寻宝图」地图海报；图片存后台可下载，或发给指定邮箱。

已有的、方案要依靠的事实（读代码确认过）：
- 定时：`nanbanqiu-notify` Worker 每分钟一次（`worker/notify.mjs`），但 Workers 里跑不了浏览器，中文字体（Noto CJK 十几 MB）也超出体积上限。
- 出图：`marketing/build.py` 已有 Python + Playwright + Noto CJK 的出图流程和品牌库 `marketing/lib.py`（颜色、字体、球、颗粒、手作滤镜、文字越界自检）。
- 邮件：`server/notify/resend.mjs`（fetch，不装 SDK）；Resend 支持附件。
- 可见性：`games.visibility='private'` 只给当事人；**`tags @> {women}` 的女生局对非女生不返回时间、地点**（schema.sql「GET /api/games/:code」）；`venues.location` 有坐标、`status` 有 hidden / pending。
- 正式库连接串在 GitHub `production` 环境（要所有者批准），定时任务没法等人批。
- 仓库目前**公开**，Actions 的产物（artifact）任何登录用户都能下载。

## 决定（提议）
分三段，每段只做一件事、可单独重跑：

1. **冻结快照（9:00 准点，数据库里）**：发送程序的每分钟定时里加一步：墨尔本时间到 9:00 且今天还没有快照 → 调 `digest_snapshot(city, for_date)`（security definer，只返回可公开字段）写一行 `digests`（`unique(city, for_date)`，重跑不重复）。准点、和 9:00 的数据一致，不受 CI 排队影响。
2. **出图（GitHub Actions，9:05 起）**：`daily-digest.yml` 定时 `5 22 * * *` 和 `5 23 * * *`（UTC，夏令时 / 冬令时各一条；脚本只处理「有快照、没出图」的那一行，另一条空跑）。读快照 → `marketing/digest/` 模板出图 → 存放 → 回写 `digests.files` → 发邮件。用专门的环境 `digest`（只在 main、不要批准）和最小权限库角色 `nbq_digest`（只能执行两个函数：读快照、写出图结果；读不到表）。
3. **取用（后台）**：后台新页「每日海报」：最近 30 天缩略图、下载原图 / 打包、复制小红书文案、看这些球局**现在**是否还缺人、一键重出图。

**存放**：私有 Cloudflare R2 桶 `nbq-digests`（Pages Functions 用绑定读，后台登录后才给；Actions 只拿到对这个桶的写权限）；保留 90 天。**不放** Actions artifact（仓库公开）、**不进**仓库。

## 1. 数据口径（「明天还在找人」）
`digest_snapshot` 唯一口径，单测逐条覆盖：
- 城市 = 墨尔本；`starts_at` 落在**墨尔本当地**明天 [00:00, 24:00)（`at time zone 'Australia/Melbourne'`，夏令时切换当天也对）。
- `visibility='public'`、`status='open'`、空位 = capacity − 已确认人数 > 0。
- **排除**：女生局（标签 women）· 私人局 · 已取消 / 已满 · 发起人账号不是正常状态（§3.11）· 球场 hidden / pending / merged · 已开打。
- 只给海报需要的字段：开打时间、时长、类型、水平区间、空位 / 总人数、标签（新手友好 / 场地已订 / 开新球…，不含 women）、球场短名 + 区（suburb）+ 坐标、分享码。
- **不给发起人昵称和头像**：App 里不登录能看到，但小红书是更大的公开范围，昵称 + 固定时间地点 = 能被线下找到；海报上只说「谁都能申请」，不说是谁发的。
- 排序：开打时间 → 球场名；同球场同时段多局合并成一行写「2 局」。

## 2. 版式规则（按局数自适应，不是只有 10 这一条线）
| 明天还缺人的局数 | 出什么 | 理由 |
|---|---|---|
| 0 | 不出图；邮件写「明天暂时没有缺人的球局」+ 从宣传物料库推荐一张常用海报 | 空表海报 = 「这个 App 没人」，最伤 |
| 1–3 | 「明日精选」大卡片版（每局一张卡，信息更大） | 稀疏的表格显得冷清 |
| 4–10 | 「明日时刻表」（一张） | 用户原需求 |
| 11–40 | 「明日寻宝图」封面 + 时刻表分页（每页 ≤10 行） | 地图看得到「哪里有」，但看不出几点；小红书一帖最多 18 张，第 2 张起给列表 |
| >40 | 寻宝图按区聚合（一个区一个数）+ 列表只放最早的 30 局，并写「还有 N 局在 App 里」 | 图里塞不下也看不清 |

全部 **1080×1440（3:4）**——小红书信息流按 3:4 裁封面，用现有 4:5 会被切掉标题和品牌标（SKILL「其他尺寸」已提示要 `lib.set_size()`）。按 2 倍（2160×2880）渲染再缩到 1080 宽输出 PNG + 一份 JPEG（质量 92，sRGB），小红书二次压缩后小字也不糊。

## 3. 视觉设计
遵守 `.claude/skills/nanbanqiu-poster/SKILL.md` 与 `品味手册.md`：深绿 + 荧光黄绿，球是主角，陈述句、句号收尾、无感叹号；文字克制，画面是主角。

**明日时刻表**（像车站发车牌，但是纸质的、温暖的，不借任何交通公司标识）
- 顶部：小标签 `TOMORROW · MELBOURNE`；标题两行「明天，」/「还有 17 个空位。」——**数空位不数局数**，更像邀请，第二行荧光黄绿。日期写「11 月 9 日 · 周日」。
- 按「上午 / 下午 / 晚上」分段，段名用细线 + 小字分隔；夜场段的底色略深（灯光意象）。
- 每行三列：**时间**（等宽数字，大号，`07:30`）· **地点**（球场短名粗体 + 区名小字）· **右侧**：类型小图标（单打 / 双打 / 拉球）+ 水平胶囊「UTR 3.0–4.0」+ 空位圆点（●●○○ = 共 4 人还缺 2，空位用荧光黄绿，**一眼看出缺几个**）。标签只放最多 1 个（新手友好优先）。
- 行高 ≥ 96px，正文 ≥ 30px（1080 宽），最小字 ≥ 24px；最长球场名按短名截断，不缩字号。
- 底部：二维码（深绿，留白 4 格，旁边写「扫码看明天的球局，申请加入」）+ `nanbanqiu.app` + 小字「截至 9:00 · 实时以 App 为准」。品牌字标照 SKILL（浅色底加深绿条）。

**明日寻宝图**
- 底图：一次性从 OpenStreetMap 数据（海岸线、菲利普港湾、雅拉河、主干道、CBD）简化成品牌风格的 SVG 底图（`marketing/digest/base_melb.svg`，固定投影和范围，提交进仓库），套 `rough` 手作滤镜 + 纸纹 `grain(light=True)`，奶油底、深绿线条；角落小罗盘和比例尺；右下 `© OpenStreetMap contributors`（ODbL 要求署名）。**不用 Google 静态地图截图**（条款限制商用和缓存）。
- 每个有球的球场是一颗小网球钉（lib 的球），球上写编号；同一球场多局 → 球旁小角标「×3」；距离太近的钉子按网格聚合，标签做避让（单测覆盖不重叠）。范围外的（如吉朗）放在边缘箭头「→ 吉朗 2 局」。
- 一个「✕」标在空位最多的地方，旁边一句小字「这里明早最热闹。」（寻宝的会心一笑，不喊口号）。
- 左上标题「明天，墨尔本有 23 个空位。」；编号对应第 2 张起的时刻表（时刻表那一列加编号）。

**统一的质量线（出图脚本自动检查，不靠人眼）**：文字不出画布 / 不互相压住（复用 build.py 的检查）· 二维码能被解码回预期网址（用 zbar / opencv 解码校验）· 对比度 ≥ 4.5:1（小字）· 固定字体版本、固定随机种子（同一快照重出图逐像素一致）。

## 4. 链接与归因
- 二维码 / 网址指向 `https://nanbanqiu.app/melbourne/?date=<明天>&source=xhs_<MMDD>`：打开就是**明天那一天**的发现页（需核实前台是否支持 `date` 参数，不支持就作为 PR 之一补上，流程 B）。
- `source` 进现有埋点，每周 `metrics` 周报加一行「小红书扫码 → 申请 → 成局」，用数据决定这件事值不值得每天做。
- 列表每行可加分享短码（`g/7Kq2`），读者想要某一局时直接输入；默认不加，避免版面拥挤（D6）。

## 5. 邮件与小红书文案
- 9:10 前后发到收件人（D4）：标题「明天的球局海报 · 11 月 9 日 · 17 个空位」；正文附 1–N 张图（附件）+ 自动生成的**小红书文案**（标题 ≤20 字、正文 3–5 行、5 个话题如 #墨尔本网球 #墨尔本生活 #网球搭子，按版式和星期从文案池挑，避免天天一样）+ 后台链接。
- 发件人 `digest@nanbanqiu.app`（Resend 已验证域名）。收件人邮箱属于个人信息：先放 GitHub 环境密钥 `DIGEST_TO`（逗号分隔），后台管理收件人留到 PR 7。
- **不自动发小红书**：没有开放接口，自动发帖违反平台规则，人工发帖也能顺手确认内容。

## 6. 可靠性
- **幂等**：快照、出图、邮件三步各记状态（`digests.status`: snapshot → rendered → mailed / failed + 错误码），任何一步重跑只做没做完的。
- **CI 定时会晚或被丢**：两条 schedule + 幂等；9:45 发送程序检查「今天的快照还没 rendered」→ 推送提醒所有者，并可在后台点「重出图」（`workflow_dispatch`）。
- **数据变化**：图是 9:00 的样子；后台页旁边显示每局**现在**的空位，发帖前已满的标灰并提示重出图。
- **库连不上**：快照那步在下一分钟自动再试（到 10:00 为止）；之后进 9:45 的提醒。
- **开关**：`app_config.digest_enabled`（默认关），先在测试库每天跑一周，再开正式。
- **城市扩展**：所有函数带 `city` 参数，底图按城市一份；悉尼上线时只加底图和一条配置。
- **成本**：每天 1 次约 2 分钟 Actions（仓库改回私有后约 60 分钟 / 月）；R2 免费额度内；Resend 每天 1 封。

## 9. 第二版样稿带来的修订（11-08，`marketing/digest/` 原型 v2）
- **加入入口改为球局码**：读者在自己手机上刷小红书，图里的二维码扫不了（要截图再识别）。每行右边印球局码，主入口写「浏览器打开 nanbanqiu.app/g/球局码」（现有短链接，不用新功能）；二维码缩小，标「微信长按识别」，只服务转发到微信 / 电脑的场景。
- **固定组图**：封面（时刻表或寻宝图）→ 时刻表分页 → 寻宝图 → 「怎么加入」固定页；每期带期号（`NO.23`）。
- **读者看得懂**：水平用「中级 · UTR 3.5–4.5」（叫法待定，D10）；空位圆点加图例；「缺 1」写成「最后 1 位」；「新手友好」做成实心标签，其余标签降为小字。
- **社会认同与本地细节**：页脚写「上一期 9 局在找人，最后成了 7 局」（从库里算）；副标题带明天天气和日落时间（D11：天气数据来源）。
- **排版技术**：表格类改 HTML/CSS（自动换行、截断、对齐），地图留 SVG；标签宽度用真实字体测量；数字用 Inter 等宽数字；地图按数据自动取景并保留海湾一角。
- **出图闸门**：文字出界 / 压住 / 截断、二维码解码、数字核对（页面文字逐字 + 标题数字 OCR 必须完全相等）。任何一项不过就不发邮件，改发「今天出图失败」提醒。
- **还要做**：随机快照压测排版（0–60 局、超长球场名、全挤一区、全夜场）；字体与 Chromium 打成固定镜像；后台「发布包」（按顺序编号的图 + 标题正文话题 + 发帖前核对清单）；后台记每期小红书点赞 / 收藏，与扫码 → 申请 → 成局一起看，按月调模板；每期记模板版本号。
- **出图闸门再加一项**：颜色对比度自动检查（正文 ≥ 4.5:1，大号数字 ≥ 3:1），Rally 版的热红在黄绿上 3.0 是手算的。
- **尺寸（11-08 定）**：小红书一律竖版 3:4（双列信息流里 3:4 封面面积是 4:3 横版的约 1.8 倍；一般按首图比例显示整组，不竖横混用，发帖前在草稿里核实）。按 1080×1440 设计、2 倍渲染，导出 1440×1920 JPG（质量 92）上传。黑板报用「立式小黑板」（竖的挂板 / 门口小黑板）理解，不硬做横版；横版 4:3 只在朋友圈、公众号、打印时另出。
- **黑板报创意筛选标准（所有者 11-08 点评后定）**：学校场景必须正好对应「报名加入一局」这个动作、是大家真说过的话（点名喊「到」、传纸条打勾、占座「这里有人吗？」）；应用题这类硬套的不用。
- **模板系统（11-08）**：黑板报拆成「皮肤 × 创意」。皮肤每周一换（6 套：赶集 / 春日 / 夜场 / 花园 / 线描 / 国风），创意每天轮换（点名册 / 传纸条 / 占座），共 18 种组合，`chalkframe.pick(日期)` 决定当天用哪个。以后加节日皮肤（春节、中秋、澳网季等，只用通用元素、不用赛事标识）只需在 `SKINS` 里加一项，按日期优先于轮换。
- **教室墙场景（11-08，所有者提「好好打球，天天向上」）**：黑板挂在墙上，上有红字标语 + 挂钟，下有彩色墙贴 + 书架；标语和墙贴每周换，和皮肤、创意一起轮换。文案改编自校园标语，只改成打球的事，不用真实学校、班级名。
- **新依赖**（随本 ADR 批）：霞鹜文楷（黑板版）；segno、zxing-cpp、Tesseract（chi_sim）、Inter 字体。

## 否决的方案
- **Worker 里用 satori / resvg 出图**：要新依赖，中文字体子集化后仍超体积上限，且和现有 Python 品牌库是两套画法、长期两边维护。
- **Cloudflare Browser Rendering**：要付费附加项和新的绑定，换来的只是「在 Cloudflare 里」，可靠性不比 Actions 好。
- **后台浏览器里现画**：管理员不打开就没图，也发不了邮件，不满足「每天自动」。
- **GitHub Actions 直接 9:00 查库**：CI 定时常晚 5–30 分钟甚至被丢，数据就不是 9:00 的；也要把正式库读权限给 CI。改成「数据库准点冻结、CI 只读快照」。
- **Actions artifact / 提交进仓库**：仓库公开，任何人能下载。

## 后果
- 好处：数据准点、出图可重跑可复现、权限最小、品牌风格和 84 张海报一致；每段失败都有提醒和重跑入口。
- 代价：新增一个库角色、一个 GitHub 环境、一个 R2 桶、一张表、一组后台接口和一个后台页；底图要一次性制作。
- 以后：悉尼加一张底图；同一套快照可复用到「每周精选」、公众号头图（2.35:1）、App 内「明日看点」。
