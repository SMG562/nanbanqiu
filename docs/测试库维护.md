# 测试库维护（nanbanqiu-staging）

依据：#98 方案 B（所有者 11-07 同意）。目标：测试库**始终跟着 main 走**，不额外花钱，不加新的基础设施。

## 平时怎么进测试库
| 情况 | 怎么做 | 谁 |
|---|---|---|
| 迁移合并进 main | Actions `staging-migrate` 自动触发（push 到 main 且迁移文件有变化），审批后执行 | 所有者合并时顺手批准 |
| 没合并、但必须用真机看库结构变化（少数情况） | 手动运行 `staging-migrate`，`ref` = 分支名；迁移必须只加不改、过两道检查 | 协作者触发，审批人批准 |
| 迁移被检查拦下（建角色、改权限、动态 SQL 等） | 不走流程，所有者看过后在 Supabase SQL Editor 手动执行 | 所有者 |

只做功能自查、不需要真机时，用不着进测试库：协作者在自己的会话里起「本地全栈预览」（分支后端 + 本机 PostgreSQL），不碰测试库。

## 会留下什么
手动执行过的「没合并的迁移」，如果 PR 后来被关掉，或者迁移内容改了，测试库里会多出 main 里没有的表、列、函数或策略，以及 `schema_migrations` 里的对应版本。

## 怎么发现
- 规矩是「先在正式库执行迁移，再合并」，所以合并后测试库和正式库应该一致。
- 运行 Actions `db-parity`（只读）：**测试库比正式库多出来的东西 = 没合并的迁移留下的**。正式库比测试库多出来的，说明测试库漏执行了，用 `staging-migrate` 补上。
- 另一个信号：测试库 `schema_migrations` 里有、main 的 `server/migrations/` 里没有的版本。

## 怎么清理（默认做法，所有者可以改）
1. **关掉带迁移的 PR 时**，作者在 PR 里写一段清理 SQL：只删这个 PR 加的对象，最后 `delete from schema_migrations where version = '…';`。这段 SQL **不放进 `server/migrations/`**（迁移只往前）。
2. 所有者审过后，在测试库的 Supabase SQL Editor 执行。
3. 再跑一次 `db-parity`，测试库和正式库一致就算完成。
4. 兜底：每次上线闸门前跑一次 `db-parity`，发现遗留就按 1–3 处理。

## 不做的事
- 不做「每个 PR 一个独立数据库」：成本和接线工作量都不合算（#98）。
- 不写「整库重置」步骤：涉及 Supabase 上没核实过的操作；真要重置，所有者先在 Issue 里定方案。
