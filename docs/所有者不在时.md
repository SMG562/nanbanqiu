# 所有者不在时：异步决策与持续开发

目的：所有者休假、几天不在线时，开发不停；但**会碰到用户和数据的那一步**仍只由所有者做。原则来自开源项目常用的「懒惰共识（lazy consensus）」：提案公开、给出期限，期限内没人反对就按提案先做；**先做的只能停在分支上**，合并时所有者仍可推翻。

## 1. 永远不委托的四件事（没有静默通过）
1. **合并到 main**（分支保护：PR + 所有者批准，CODEOWNERS 强制）。
2. **正式库、部署、密钥、Cloudflare / Supabase 设置**。
3. **改游戏规则**：CODEOWNERS 覆盖的文件（含本文件、`CLAUDE.md`、`.github/`、`tools/`、`docs/adr/`）。
4. **对用户公开的隐私 / 法律文案**（`privacy.html`、`隐私清单.md`）。

## 2. 按改动分级决定「能不能先做」（分级见 `协作实践.md` §11）
| 级 | 所有者不在时 |
|---|---|
| A 文档文案 · B 界面 | 照常做、照常开 PR，等所有者回来审 |
| C 接口与用户数据 · D 库结构 / 公共层 / 公共接口 | **提案 + 静默期**（见 §3）：提案发出就可以在分支上开工，期满没人反对算「暂定通过」 |
| E 安全与权限 | 可以在分支上起草；合并前必须所有者批 + 独立复核（另一个不看原过程的 AI 会话只读复核也算），**没有静默通过** |

## 3. 提案 + 静默期（C / D 级）
1. 在 Issue 里发提案：要解决什么、方案、否决了什么、回退办法、影响面；最后一行写 **「静默期：到 YYYY-MM-DD（墨尔本时间）」**，至少 **2 个工作日**；所有者发过离开公告的，以公告里的回来日期为准（取较晚的）。
2. 期限内所有者或其他协作者提出反对 → 停，等讨论。
3. 提案发出后就可以在分支上开工（分支不影响任何人，返工风险自担）。期限到、没有反对 → 在提案下面回一条「静默期已过，暂定通过」，之后别的协作者可以在它上面接着做。这条决定标为**暂定**，不写进 ADR / 进度记录；所有者回来批了才算定。
4. 先做的东西必须：**功能开关后面、默认关**；迁移**只加不改**、可重复运行；PR 描述第一行写「暂定实现，依据 #Issue 的提案（静默期到 YYYY-MM-DD）」。
5. 所有者回来推翻 → 返工由提案人承担，这是先做的代价；分支不合就等于没发生。

## 4. 叠加 PR（一条功能线）
- 后一层依赖前一层还没合并的改动时，用叠加 PR：第 N 层的 base 是第 N−1 层的分支；**每层仍 ≤ 200 行**、各自 CI 绿。
- **一条叠加链算一个在制品**（`协作实践.md` §1 的「每人 ≤ 2 个」按链算）；链长 ≤ 5 层，超过先停下等合并。
- 合并从最底层开始；底层合并后，把下一层的 base 改成 main，再 `git merge origin/main`（不 rebase、不强推）。
- PR 描述第一行写清链条：`A1 #81 → A2 #82 → …（本 PR）`。

## 5. 所有者离开前（5 分钟）
在 Issue 里发「离开公告」（标签 `协作体系`）：离开和回来的日期；这段时间**预先同意**的事（例如「#60 的 A4–M2 可以在分支上做」）；紧急情况联系方式和止血办法（`出事处理手册.md`：回退 / 关开关）。预先同意的事不用等静默期。

## 6. 所有者回来后（建议顺序）
1. 先看 E 级 → D 级 → C 级的 PR；叠加链从底往上审。
2. 每个「暂定」决定：批（摘进 ADR / 进度记录）或推翻（在 Issue 里写原因）。
3. 需要在测试库跑的迁移，按链条顺序一次跑完（`node tools/migrate_bundle.mjs`）。

## 7. 安全加固（所有者在 GitHub 设置里做，一次性）
1. **部署用的密钥只放进受保护的环境**：`deploy-notify.yml` 用的 `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` 如果是**仓库级** Secret，任何能推分支的人在自己分支加一个 workflow 就能读到（main 的分支保护拦不住）。改法：Settings → Environments → `production`（已有，`db-parity` 在用）→ 把这两个 Secret 移进去，Deployment branches 只允许 `main`，并给 `deploy-notify.yml` 的 job 加 `environment: production`；仓库级的删掉。
2. Settings → Actions → General：Workflow permissions 选 **Read repository contents**（默认只读令牌）。
3. 规则集里打开「新推送后撤销旧的批准」（dismiss stale approvals），防止批准之后再塞进改动。
4. 协作者和 AI 助手只用 fine-grained 令牌、只授权本仓库、不给 Admin。
5. 测试库迁移（让协作者在所有者不在时也能在预览站看效果）：可选。做法是只加一个手动触发、绑定 `staging` 环境（需要所有者或指定的人批准才运行）的 workflow，只能执行仓库里已有的迁移文件；**不给协作者测试库连接串**。是否要做、谁能批，由所有者定。
