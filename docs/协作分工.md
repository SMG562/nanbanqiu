# 协作分工与消息协议（多会话并行）

目标：所有者侧 2–3 个会话 + 协作者的会话同时开工，**不撞车、不重复、不等人**。原则见 `协作实践.md` §14（能不共享就不共享）；这里只写角色、开工流程、合并列车和消息格式。数据来源：近 14 天 479 个提交，热点 `进度记录.md` 221 次、`tests/run_all.mjs` 69 次（`node tools/overlap_check.mjs --hot` 实时算）。

## 1. 角色（按职责，不按人）
| 角色 | 谁 | 独占的事 |
|---|---|---|
| **集成者** | 所有者侧的**一个**会话（同一时间只有一个） | 合 main（`pr_merge.sh`）、红线 PR、改 `进度记录.md` / `业务规则.md`、正式库迁移与部署、安排独立复核、每天收尾同步 |
| **建造者** | 每个会话 = 1 个 Issue + 1 个分支 + 1 段文件范围 | 只推自己的分支；功能 PR 不改 `进度记录.md`；做完留【求复核】 |
| **复核者** | 一次性只读子会话（`tools/review_prompt.md`），**双方交叉**：协作者侧复核所有者的非红线 PR，所有者侧复核协作者的 | 不留状态，结论只写成 PR 留言；不复核自己写的；留言写看了什么 / 跑了什么 / 没验证到什么；说「要改」后作者修完，重审或明说「按建议修，未再复核」由合并的人定；红线 PR 的复核仅供参考（只有所有者合）；E 级（登录、令牌、RLS、隐私）所有者侧再看一遍 |
| **所有者本人** | — | 只做三类决定：红线合并、产品拍板、真机验收。其余按常设授权，不用问 |
别的会话看到 PR 想合：不合，留言【求合并】。两个会话同时当集成者 = 合并顺序打架，是最贵的冲突。

## 1b. PR 归谁管（11-12，#185 事故后）
**事故**：#185 被同一账号的两个会话在 22 秒内先转 Ready、又转回草稿（原因是后者想按 #167 的顺序排队）。根因不是谁手快：GitHub 上同账号的几个会话看起来是同一个人，**没有任何约定说这个 PR 归谁改状态**；再加上 PR 评论 / CI 会叫醒订阅了它的会话，被叫醒的会话以为「该我处理」，就接着动手。行业共识同理：并行 AI 的冲突靠「边界先于协调」（每个资源只有一个写入者），不靠事后谈判；GitHub Copilot 编程智能体自己也不能把 PR 转 Ready、不能合并，这一步留给人。
1. **一个 PR 只有一个主人 = 它的分支所属的会话**（一会话 = 一 Issue = 一分支 = 一组 PR，本来就一一对应）。**草稿 / Ready / 关闭 / 改标题 / 改 base 只有主人能做**；改状态一律 `bash tools/pr_state.sh <PR号> ready|draft`——当前不在那个分支上就拒绝。
2. **别的会话（含集成者、复核者）想让它变状态**：在 PR 上留一条【请转草稿】或【请转 Ready】+ 理由，然后停。不要「顺手」改。唯一例外是所有者当场点头的 `NBQ_PR_OVERRIDE="原因"`，会自动留痕。
3. **排队顺序不靠改草稿表达**。#167 定的先后由集成者按看板（#170）和 `pr_merge.sh` 安排合并顺序；前面的还没合，后面的照样可以 Ready，轮到了才合。要等前面的合了再 Ready，那是主人自己的决定，写在 PR 描述「依赖：#」。
4. **被叫醒先过唤醒闸门**：第一步 `bash tools/pr_state.sh <PR号> mine`（退出码 0 = 我的；3 = 不是）。只有主人会话订阅 PR 活动。别的会话被叫醒（评论 / CI / 部署机器人）发现不是自己的：不改状态、不推提交、不回应机器人评论；确有要说的只留一条带标签的评论，然后取消订阅。主人会话结束 / 交接前也取消订阅，并在 #161 写【交接】（新会话接手就是新主人，在 PR 留言【接手 PR #n】）。
5. **留言一律走 `bash tools/pr_say.sh <号> <标签> <提交号|-> "<正文>"`**：自带去重（同标签 + 提交号 + 正文只发一次），所以两个会话不会各回一遍、同一个失败不会重复评论；机器人（部署、看板）和自己的评论一律不触发动作。新标签：【请转草稿】【请转 Ready】【接手 PR】。
5b. **机器兜底**：`collab_board` 发现 PR 状态 10 分钟内被改 ≥ 2 次，会自动在该 PR 上提醒（含归属规矩），同一次抖动只提醒一次——规矩在出事那一刻自己出现，不用等对方重开会话。
6. **改 `CLAUDE.md` / 本文件 / `tools/` 这类共享规矩的 PR 只开一个主人**，其他会话要改走 Issue 提案。

**为什么这样设计**（给想改规矩的人）：① 用「分支 = 会话」当身份，因为所有会话共用一个 GitHub 账号，账号分不出人，分支能；② 用脚本拦而不是靠自觉（本仓库「能被脚本拦的规则只留一行」）；③ 不引入新工具 / 新标签，改状态这一个动作收口；④ 仍没解决的：脚本只拦走脚本的人，直接点网页按钮或调 API 绕得过去——所以第 4 条「别订阅别人的 PR」是第一道防线，`collab_board` 以后可加「状态在 5 分钟内被改两次」的告警。

## 2. 开工 30 秒（建造者）
1. `node tools/overlap_check.mjs [要改的文件/目录…]`（不带参数 = 当前分支已改的）：列出别的开着的 PR 同改了什么、哪些是热点。有撞车 → 先串行（等那个先合）或换范围，不要两边都做。
2. 在 Issue 里发【认领】（文件范围必填，同 Issue 模板「文件范围」）。
3. `bash tools/new_branch.sh <名>` 从最新 main 开分支。等复核的自己的 PR ≥ 3 个时不开新功能，只做复核、修偶发失败、给自己的 PR 合 main（排队越多越容易落后 main、冲突、重跑 CI）。**热点文件**（`--hot` 列出的）单独成小 PR、先合，不和大功能混在一起。

## 3. 合并列车（集成者）
- 按「Ready 的先后 + 红线优先」一个一个合；**只对队首 PR 做 `sync_main.sh`**——同时给几个 PR 合 main，每个都白花一轮 CI。
- 队首「不能快进」才 `sync_main.sh`（旧分支没有这个脚本：`git show origin/main:tools/sync_main.sh | bash`）；它会自动处理 `.list` / `tests/run_all.mjs` 的各加一行、和旧分支带着的生成文件，真冲突才中止。已知边界：union 遇到「一边删某行 `add()`、另一边改它」会把改过的那行留下，合并后看一眼 `node tests/run_all.mjs --list` 数量；`add()` 重复 id 会直接报错。
- 复核留言在「只多合并 main」时自动沿用（`tools/review_carry.mjs`，判据：PR 改过的每个文件内容逐字节相同 + main 新增的没碰 PR 的文件；缩进 / 挪行都算「不一样」）；不满足才重审。CI 仍对新提交跑一遍。
- 合完一个，`bash tools/overlap_check.mjs --prs` 看下一个有没有新的撞车。

## 3b. 复核自动巡检
「球在复核」（非草稿 + CI 全绿 + 级别需要复核 + 还没通过）由 `node tools/review_queue.mjs` 列出；两边各有一个定时会话按 `tools/review_sweep.md` 复核**对方**的 PR（只读、只留言、不合并），所以转 Ready 后不用通知谁——看板会标「球在复核」，最迟几小时内就有复核留言；「要改」会 @ 作者。流程改在 `tools/review_sweep.md`，不用改定时任务。

## 4. 消息协议
**Issue / PR 评论第一行写固定标签**，人和脚本都能扫（球在谁手里仍由 `collab_board` 自动标，不手写）：
| 标签 | 谁发 | 必写内容 |
|---|---|---|
| 【认领】 | 建造者 | 文件范围、预计几个 PR、依赖谁 |
| 【阻塞@谁】 | 任何人 | 卡在什么、需要对方做什么（超过半天就发） |
| 【求复核 <7位>】 | 建造者 | 改了什么、风险、怎么回退 |
| 【求合并 <7位>】 | 非集成者 | CI 绿、复核留言在哪 |
| 【已合并 <7位>】 | 集成者 | main 现在是哪个提交、谁要 `sync_main` |
| 【交接】 | 会话结束前 | 现状（实测）、下一步顺序、踩过的坑——写在 #161 最新一条，下个会话以它为准 |
一条消息只讲对方的下一步；需要对方定的事写成「默认 + 理由 + 24 小时」，对方只回编号。**24 小时没回复按默认做，只适用于流程 / 测试 / 文档类**；部署、密钥、正式库、删除、对外发布、红线合并只听所有者当场点头，沉默不算同意。进度不经任何一方转达：看看板 #170 和 PR 本身。决定写在 Issue，聊天里定的事当场回写。对方是机器（脚本 / CI）的事，不用写消息，让它自己说。

## 5. 度量与进化
每周一看三个数：`合并 origin/main` 次数（目标 ≤ 1/天）、PR 从 Ready 到合并的中位时间、被取消 / 重跑的 CI 次数。同类冲突出现第 2 次 → 改结构（拆文件、union 合并、登记成自动处理），不靠自觉。

## 6. 双向同步（自动，不靠聊天、不靠人转达）
- **规矩只有一个来源：仓库文件**（CLAUDE.md、本文件、开发规矩.md、协作实践.md、docs/adr、.claude/skills）。改规矩的提交说明以「协作：」开头。
- **收**：每个会话开工跑 `bash tools/handoff_check.sh`，「近 7 天协作规则变化」会列出两边改过的规矩文件（含本文件、开发规矩.md）；长跑的会话被叫醒时看「规矩水位线」（上次读到的 main 提交）之后的 `git log -- <规矩文件>`，有大改就交接、换新会话。
- **发**：一边验证有效的做法（跑通 3 天、没有反例），用 PR 写进本文件或开发规矩.md（非红线，自助合并）；涉及红线文件（CLAUDE.md、协作实践.md、docs/adr、.claude/）的，开提案 Issue，附可直接替换的原文。
- **每日复盘**：两边各有一个定时会话，读对方的规矩变化、核对自己有没有违反、把验证过的做法外发。协作者侧的状态和守则在 #191「管家状态」留言。
- 只有红线和真正的分歧才单独沟通，写成「默认 + 理由 + 24 小时」。

## 7. 协作者侧工作方式（11-12 起；所有者侧可参照采用）
1. **在制品 = 1**：同一时间只推进一个 PR，合并后再开下一个；最多 1 个管家会话 + 1 个建造者会话。
2. **当天合**：开工前把 PR 切到一天能做完、测完、合完；活过 24 小时就拆小或关回 Issue。
3. **先查决定卡，再找所有者**：`node tools/decision_card.mjs <PR>` 的「需要所有者做」是「无」且不是红线 → 自己做：复核靠所有者侧巡检、真机由协作者本人、合并自己 `pr_merge.sh`。
4. **低风险直接合**：决定卡「无需复核」的，CI 全绿就合，不排队。
5. **真机攒批**：要真机的事攒成每天一张清单，一次做完。
6. **不写机器口令**：复核结论的固定句式只在真复核时写（11-12 #114 引用原文被看板误判成通过，见 #201）。
7. **一台机器同时只跑一套重测试**；并行改代码用 worktree，测试排队。
