# 审阅协作者的更新（所有者侧）

目标：**用最少的 token 把「协作者做了什么、哪里有风险、所有者要做哪几步」讲清楚，并把每次发现变成不会再犯的东西。** 先确认身份：`gh api user --jq .login` 是 `SMG562`；不是就停（协作者的 AI 读 `collaborator-pitfalls`）。

## 一、盘点（≈ 5 个命令，别逐个打开 PR）
1. `bash tools/handoff_check.sh`：进度记录落后于实际的部分（提交 / 开着的 PR / CI）。
2. 会话里 `gh pr view` / `gh issue list` 走 GraphQL，**会 403**；一律 REST：`gh api repos/SMG562/nanbanqiu/pulls/<号> --jq '…'` 和 `…/pulls/<号>/files --paginate --jq '.[]|"\(.status[0:1]) \(.filename) +\(.additions)/-\(.deletions)"'`。
3. 先读协作者自己整理的交接（Issue「所有者回来后」类，如 #108）和「经验」类 Issue（如 #113）——它们通常已经排好顺序，**直接复核它，别重新发明清单**。
4. 按 `协作实践.md` §11 与 `docs/adr/0010` 分级：**红线**（正式库、部署与密钥、隐私文案、闸门本身、规则文件）只有所有者在当前对话点头才合；红线以外（A–E）满足「CI 绿 + 描述核对 + 独立复核」就自助合并，不要等所有者。
5. 只对**文档类**读补丁（`/pulls/<号>/files` 的 `.patch`）；代码类先看文件清单和行数，再决定读哪几个文件。

## 二、逐类核对（每类一句话判断 + 证据）
**文档 / 规则 / ADR**
- 与现行规则一致吗？拿它说的事实去 grep：业务规则 §、`CLAUDE.md`、`docs/adr/`、代码里的真实名字（表名、文件名、函数名）。例：#107 修的 `event_dictionary` 实为 `event_definitions`。
- 描述的东西**现在存在吗**？依赖未合并的 PR → 合并顺序写进结论（例：#99 要等 #95）。
- 时间是否标了时区（默认墨尔本；GitHub 页面的时间是 UTC）。
- 体量：`tests/spec/doc_budget.json` 预算只降不升；加内容的 PR 是否同时删了等量旧内容。
- 隐私：新增个人数据（球拍、UTR、球友…）→ `隐私清单.md` + 公开 `privacy.html` 都要写，打开开关前补齐。
**代码 / 迁移**
- 入口清单是不是 grep 出来的；迁移是否只加不改、可重复、处理已有数据；`schema.sql` 与迁移一致；是否改了公共层（`0130 0140 0155 0495`）并写「影响面 × 反例测试」。
- 手写行数（目标 ≤ 200）；同一例外第二次出现 → 提议改规矩，不逐次放行。
- 用 `bash tools/pr_merge.sh <号> --check` 看闸门（只核对，不推）。
**流程 / 脚本**
- 用 git 输出的**文件名做匹配**的脚本，必须 `-z` 或 `core.quotepath=off`（中文名会被加引号，`tests/unit/git_paths` 守着）。
- 新闸门先对照 `pr_merge.sh` 等自动推送路径是否冲突。

## 二b、怎么批（11-13，#229/#241 定下的做法；2–3 人团队按这个省时间）
1. **先判可逆性**：可 revert、只放宽不新增拦截、合并后有兜底 → 当天在 Issue 里一句话「同意 + 一个条件」，别开多轮；不可逆（正式库、部署、密钥、隐私）才走完整复核。
2. **先问根因，再看补丁**：被反复重跑 / 卡住，先查是不是流程用法问题（例：库结构 PR 该小而先合，§8），放宽规则只当兜底。
3. **一条规则只留一份实现**：两处各写一份判断（pr_merge.sh 与 merge_gate.mjs）迟早分叉；批准时的条件就是抽成共用 + 两边同场景同结论的测试，不靠合并顺序或人记。
4. **复核力度按改动量**：几十行脚本 + 有测试 → 所有者 / 共同所有者自己读 diff，比冷启动子会话便宜；子会话留给大改动和不可逆动作。
5. **反馈固定一条**：`bash tools/pr_say.sh <号> 拍板 <提交号> "同意/不同意 + 条件 + 顺序"`，协作者的分支只留言不碰状态。
6. **不串行等（11-14 所有者定，往后都按这个）**：① 独立复核在代码定型就开始（别等转 Ready / CI；只多合并 main 时沿用，`review_carry`）；② 所有者「同意」一次给全：写明范围提交号 + 条件（复核通过、CI 绿、之后只多合并 main），条件满足由会话直接合，不再来一轮；③ **合并与开启拆开**：新能力用环境密钥 / 开关默认关着合并，所有者另选时间打开，回退 = 关掉；④ 所有者的动作（正式库迁移、设密钥、真机）攒成一个集中时段，一条清单列全，别零散问；⑤ 迁移幂等、只加不改，所以复核改了迁移就让所有者重跑一次，不为它停下。
7. **每周一次**看 metrics 周报：在制品、前置时间、重跑次数；某条规则一个季度没拦过事就提议删，流程提案同时只开一个、合并后观察一周。

## 三、不绕过
红线动作（正式库迁移、部署、隐私文案、闸门本身）被系统或自动模式拦下 → **停，说明要做什么、为什么，让所有者在对话里点头**；不换命令绕。红线以外被拦，先查原因（多半是缺 CI 或缺独立复核），补齐后自助合并。独立复核要另开一个没看过本次过程的会话：用 Agent 工具照 `tools/review_prompt.md` 的模板开只读子会话（不花 API 费用），结论留言「独立复核：通过 <7位>」；`.github/` 的机械问题由 `workflow-lint` 先拦。

## 四、产出（四处，各一个落点，别重复写）
1. **结论**：写进 `进度记录.md`「审阅结论」段（一行一个 PR：✅ / ⚠️ + 证据）；顶部「现在在哪 / 新对话第一件事」同步；超过 20KB 先瘦身，旧文原样进 `进度记录_历史.md`。
2. **漏洞**：每个流程类漏洞一行进 `逃逸缺陷.md`（现象 · 根因类别 · 为什么漏 · 拦截）；**同类第二次出现必须做成自动检查**（单元测试 / precommit / CI），不是再写一条规矩。
3. **反馈**：给协作者的话发 Issue（标「协作体系」），固定结构：**做得好（保持）→ 请改进（按影响排序，每条带证据和「做法」）→ 下一轮请你做（勾选框）→ 所有者一侧也改了什么（对等）**。样板：#118。只对事不对人；每条能追溯到 PR / 提交；协作者可以回复反驳。
4. **可复用的做法**：协作者该学的 → `collaborator-pitfalls` §七；审阅方法本身变了 → 改本文件。**规则文件（`CLAUDE.md` `开发规矩.md`）最后才动，只加一行指针，且先删等量旧内容。**

## 五、让它自己进化（每次审阅末尾做 2 分钟）
- 本次花时间最多的一步是什么？能不能变成脚本（同一手工步骤做过 3 次就写脚本）？
- 有没有「靠人记」的核对？能不能变成测试？（例：中文文件名 → `git_paths`；文档预算 → `doc_budget`。）
- 协作者的哪项做法值得推广？写进 §七 和样板，并在反馈里点名。
- 本文件超过 ~7KB 或有条目一个季度没用到 → 精简。
- 度量（`metrics` 周报，每周一）：在制品、前置时间、不稳定测试、CI 分钟。**在制品 > 评审能力 = 先停开新功能**。

## 六、省 token
- 先 `--jq` 压缩字段再读，文件清单优先于补丁；长输出写 `/tmp` 只看结尾或 grep。
- 一次 Bash 里并行多个只读查询；不开子任务（所有者要求时除外）。
- 不重复读已读过的 PR；PR 之间互相依赖时一次看完链再下结论。
