# 前台状态与页面一致（南伴球 11-03～11-05 几次低级错误后定）

> 来源：所有者账号里的同名 skill，已去掉只属于所有者的步骤（部署、同步到电脑）。每一条背后都有一次真实事故，台账见 `逃逸缺陷.md`。

起因：①刷新后内存里已是登录用户，右上角却仍画着「登录」；②修好后刷新时又短暂闪出「登录」再变头像；③接真实数据后，库里存色名（paper）、前台画印要色值，默认纸白被画成黑色。三次都是「看起来有，实际画错 / 状态和画面分叉」，且测试和自查都没抓到。

## 一、设计时就要做对（不是出了问题再补）
1. **登录态是三态，不是两态**：已登录 / 恢复中 / 未登录。只写 `if(!ME)` 分不清「没登录」和「还没读回来」。所有「需要登录」的区域只走统一入口 `authView({in,wait,out})`，页面不自己判断去画登录按钮或「登录后…」。
2. **先画缓存、后台再更新**：刷新时本机有登录记录，就用上次的快照（`nbq_snap`）立刻画成登录状态，后台验证令牌并读最新数据，读完静默换上。没有快照才画「正在恢复…」占位，绝不先画「未登录」再跳变。
   - 快照期间数据可能是旧的：写操作不放行（`NBQ_STALE` 期间不写），读完解除。
   - 快照必须带账号标识；退出登录、令牌失效、换账号、过期、版本不对一律删除。
3. **数据读进内存只走一个出口 `nbqApply → nbqRenderSoon`**。不靠每个调用处各自记得 render()。重画合并成一次，用户正在输入时不打断。
4. **异步之后再检查提前返回**：读完数据再做事的代码里，逐个检查同一段的 `if(...)return` 在异步完成之后是否还成立。典型错误：`if(ME)return` 放在「读入已把 ME 设好」之后，等于跳过重画。

## 二、测试必须看页面，不只看内存
- 前台测试断言**页面（DOM）**：登录后、刷新后、令牌过期重开后、退出后、令牌被撤销后，头部和各页面是否对。
- **看过程不只看结果**：从页面一开始就用 MutationObserver 记录关键区域每次变化，断言中途没出现过「登录」/占位文字（用 innerText，不要用 textContent——会把 script 源码里的字符串算进去）。
- 加「任何一次把数据读进内存之后，页面一定重画」的断言。
- 新测试先在修复前跑一遍，确认它失败；再修，确认通过（把修复撤掉再跑一次最直接）。
- 静态检查拦「绕过统一入口」：凡直接写登录按钮 / 登录入口而不经过统一入口的，测试失败。
- 等待条件要对准真正的完成信号（如「快照标记已解除」），不要用「ME 已有值」——快照会让它一开始就有值。

## 三、修一处 bug，就要查全站同类
1. 先想清这类错误的**写法特征**，grep 全库，列清单，逐个判断。
2. 一次修完，改成统一入口，不是每处各补一个判断。
3. 补一个覆盖全站的测试，再补静态规则防新增页面绕过。
4. 汇报里说清：查了多少处、修了多少处、还剩什么限制。

## 四、验证与汇报的诚实
- 说「前台修好了」之前，在真实页面里看一眼画面（截图），不是读变量。
- 没验证到的不说已验证：真机没看过就明说；测试没跑完就说没跑完；CI 没出结果就说没出结果。
- 不编过程：分清「记录里写着的」和「我的判断」；不确定就说没查证。
- 先承认是什么性质的错误，再说怎么防，不辩解。
- **截图里看到的任何异常都不许放过**（11-09：看到卡片压字，以「原来就有、不是这次改的」略过，被用户指出）：当场修，或记进 `逃逸缺陷.md` / Issue 并告诉用户；「不是我改的」不是不处理的理由。
- **画面要在用户的真实环境里看**：时区不是墨尔本（上海 / 珀斯 / 洛杉矶）、窄屏（320）、长场馆名。会随环境出现的内容（如「当地 HH:MM」）跑 `frontend/layout_tz` 量出来，不靠一种时区一张截图。

## 五、流程教训
- **先拿证据再下结论**：别用「最可能是…」当结论；先查日志、截图、数据。
- **杀进程别用会匹配到自己命令行的写法**：`pkill -f run_all.mjs` 会把执行它的 shell 一起杀掉；用 PID 杀。
- **跑到一半别重新构建**：测试在跑时又 build 会让结果混着两版代码。
- **「只改了一端」要明说**：手机端（PWA）和网页端（Web）分别验证，没验证的那端要告诉评审人。
- **CI 配置也要在 CI 环境验证**：本地有 playwright 的测试，在没有浏览器的快速档里会挂；新增测试时问一句「CI 的这一档有这个依赖吗」。

## 六、库 / 接口的值进前台：转换口 + 枚举覆盖（11-03 头像印色教训）
根因：同一个东西有两种写法（库存色名 `paper`，前台要色值 `#F4EFE3`），中间没有统一转换口；演示数据走色值，真实数据第一次走色名，没人转换。
1. **进前台只走一个转换口**：接口数据 → 前台对象只经 `nbqFrom*` 转换函数，页面代码不直接读原始接口字段。
2. **枚举字段用 `nbqEnum(field,val,allowed,fallback)`**：库里的值前台不认得 → 用兜底值，同时上报「未知枚举值」，**不原样往下传**，也不静默。
3. **枚举覆盖检查**（`enum_cover`）：从 schema 约束读出每个字段的全部取值，要求前台每个值都有对应处理；库加值 / 前台少值，测试先红。
4. **断言「对不对」，不是「有没有」**：测试数据里出现某个值，就断言它画出来的样子。
5. **多选 / 数组字段别只取第一个**：转换时丢信息和丢值一样是错误。
6. **schema 里「后面的语句覆盖前面的默认值」要有测试盯最终生效值**。
7. **接真实数据的改动，用预览站（测试库）+ 测试号真登录看过画面**再合并；演示模式通过不代表真实模式没问题。
8. 回答「为什么没提前发现」的五问：①同一概念有几种写法？转换口在哪？②测试数据里有触发条件吗？断言盯住了吗？③库的值域和前台值域对账了吗？④真实模式有人看过画面吗？⑤有没有「后面覆盖前面」的配置？

## 七、改完前台状态相关代码前的自检
1. 「恢复中」时画什么？（走统一入口了吗）
2. 数据读进内存之后谁负责重画？
3. 同一段里有没有异步之后不再成立的提前返回？
4. 快照/缓存：退出、失效、换账号会清吗？旧数据期间写操作被挡了吗？
5. 测试断言的是页面还是内存？修复前它会失败吗？
6. 全站同类写法搜过了吗？静态规则加了吗？
7. 我在真实页面里看过了吗？手机端呢？
8. 新读进来的字段：有转换口吗？枚举有覆盖检查和兜底上报吗？断言的是画对了吗？

## 八、用户能改的数据：写服务器 + 读回，按「入口清单」做（11-04 漏了印象、徽章已庆祝只在内存）
根因不是某行代码写错，而是做事方法：
1. **范围按「后端有哪些接口」列，而不是按「界面上用户能做哪些动作」列。** 接口清单里没有的入口永远不会被想起；测试只验证做了的，所以全绿。
2. **同一份数据有多个修改入口**（赛后卡片、球员卡、一键全选……），只接了一个。
3. 没有机械化的反向检查；没有通用的「刷新后还在」测试，最后靠用户真机发现。

固定做法：
- **开工前做入口清单**：grep 这份数据（仓库变量）的**所有**修改处，列表「入口 · 真实模式是否写服务器 · 读回在哪 · 测试」，写进 PR 描述。要从仓库变量和界面出发，不是从接口文档出发。
- **工具拦**：`tools/persist_audit.mjs`（提交前自动跑）拦「内存仓库被改却没写服务器 / 整仓库没读回」；欠账登记在 `tests/spec/persist_allow.json`（类别 local / demo / derived / todo），**新增仓库不登记就拦提交**。
- **测试必含「清空内存 → 重读 → 还在」**；失败路径断言「页面不变 + 有提示」。
- **真机清单固定两项**：「刷新后还在」「换设备 / 换浏览器登录同一账号还在」。
- 评审人报一处，就查同一仓库的所有入口。
- 做完的口径：对照入口清单逐行打勾，没勾完的写进「没做」，不说「完成」。

## 九、弹层 / 表单 / 键盘 / 输入框（11-05「说一句」输入框改了三轮才对）
Playwright 全绿、真机全红。桌面自动化没有 iOS 键盘、没有「键盘 + Safari 工具栏只剩约 200pt 可视高度」、没有「确认拼音时 compositionend 先触发，随后紧跟一个 isComposing=false 的 Enter」。**自动化测不到的环境，必须手动模拟（加 `.kb` 类、手动派发 compositionend + Enter、缩小视口到 390×330），并且真机看过。**
1. **长表单遇到键盘就折叠**：键盘弹出（`.kb`）时只留输入框 + 提交，其余折起（`.kbhide`），键盘收起后保持精简视图并给「修改」按钮；**不做固定浮层按钮**。聚焦的输入框所在区块用 `:focus-within` 豁免。
2. **有后果的操作（发送、发布、支付）不绑回车**：回车只收键盘。所有自己写的 Enter 监听必须过 `nbqImeEnter(e)`。
3. **同屏重画保滚动位置**由 `openSheet` / `openModal` 根上统一保，不靠每张表单自己处理。
4. **草稿保留一律 opt-in**（`data-keep`），不要默认对所有输入框恢复。
5. **每个输入框都登记**（`tests/spec/inputs.json`，`input_audit` 拦未登记），并有「聚焦后输入框在可视区内」的断言（`input_visible`）。
6. 评审人报一处就查所有输入框。
7. 键盘类改动**必须真机看过**才说通过；汇报里写明哪些只在模拟环境测过。

## 十、改公共层 / 推送前的流程闸门
事实：给公共弹层加了「默认全开」的重画保草稿，只测了新写的两个测试，没等相关测试跑完就推送，随后 real_chat 红。文字纪律拦不住赶时间。
1. **能用机器拦的纪律不写成「请注意」**：做成钩子 / 审计 / CI 检查。
2. **往公共层加行为 = 影响面最大**：默认 opt-in；要默认开，先 grep 全部使用方，每类写**反例测试**（不该受影响的要不受影响）。只测正例是最常见的漏洞。公共层文件在 CODEOWNERS 里，必须所有者审。
3. **固定顺序**：改 → 构建 → 相关测试跑完且全绿 → 提交 → 推送。
4. **新测试撤掉修复必须红**，否则它可能什么也没测。
5. 复盘四问：测试环境和真环境差在哪？我只修了被报的那处吗？我是不是在用浮层 / 开关绕开根因？有没有机器闸门而不是文字提醒？
